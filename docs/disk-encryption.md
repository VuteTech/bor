# Disk Encryption Policies

The **Disk encryption** policy type manages LUKS2 full-disk encryption
across a fleet. It verifies that the volumes in scope are encrypted,
enrolls automatic unlocking through the **TPM 2.0** chip and/or **Tang**
network servers, and escrows a per-volume **recovery key** on the Bor
server - turning Bor into the fleet's recovery-key directory, the role
Active Directory plays for BitLocker on Windows.

Typical uses: laptops that boot unattended while the boot chain is intact
and fall back to a help-desk-revealable recovery key; office desktops that
unlock only on the corporate network; a compliance requirement that every
system volume is encrypted with AES-256 and every recovery key is escrowed,
rotated and audited.

This page is the operator's guide: what the feature does, how the pieces
fit together, and how to run it day to day.

## Background: LUKS2 and protectors

[LUKS2](https://gitlab.com/cryptsetup/cryptsetup) (Linux Unified Key Setup)
is the standard Linux disk-encryption format. The data is encrypted with a
single random **volume key**; up to 32 **keyslots** each store a copy of
that volume key, encrypted under a different credential. Any one keyslot
unlocks the disk. **Tokens** in the LUKS2 header describe how a keyslot is
unlocked (a TPM enrollment, a Clevis binding, a recovery key) so boot
tooling finds the right mechanism automatically.

Borrowing BitLocker's vocabulary, each managed keyslot is a **protector**.
A Bor-managed system volume typically ends up with four:

```
LUKS2 volume  luks-3f2a9c1e-…  (backs /)
│
├── slot 0  systemd-tpm2      TPM 2.0, PCR 7        unattended boot on an intact boot chain
├── slot 1  clevis (tang)     tang1.corp            unattended boot on the corporate network
├── slot 2  systemd-recovery  Bor recovery key      typed at the prompt when both fail
│              └── escrowed on the Bor server, envelope-encrypted
├── slot 3  password          user passphrase       untouched by Bor
└── token   bor-escrow        unassigned marker: escrow id, keyslot, server
```

The protectors are independent: adding or rotating one never changes the
volume key or affects the others, and the machine stays bootable through
every operation Bor performs.

| Protector | Unlocks when | Managed with |
|---|---|---|
| **TPM 2.0** | The measured boot state (PCRs) matches the enrollment - i.e. firmware, Secure Boot configuration and boot chain are unchanged | `systemd-cryptenroll` (dracut-based systems) |
| **Tang** | The machine can reach the configured Tang server(s) on the network at boot | `clevis luks bind` with a pinned signing key |
| **Recovery key** | A human types the 64-character key at the boot prompt | Generated by the agent, escrowed on the Bor server |
| **User passphrase** | The user types their passphrase | Not managed; left in place |

## Architecture

### Components

```
                 ┌────────────────────────────── Bor server ───────────────────────────────┐
                 │                                                                          │
 Web UI ── REST ─┤  Disk-encryption service      Escrow store (PostgreSQL)                  │
 (reveal,        │  · volume inventory           · recovery keys, envelope-encrypted        │
  rotate,        │  · rotation task queue        · AES-256-GCM, per-record DEK              │
  fleet view)    │  · drift / clone detection    · DEK wrapped by the KEK ──► KEK file      │
                 │  · hourly janitor                                        (outside the DB)│
                 │  Tang registry (trusted signing keys, advertisement checks)              │
                 └────────────▲─────────────────────────────────────────────────────────────┘
                              │ gRPC over mTLS (:8444) - inventory, escrow, confirm, tasks
                              │
                 ┌────────────┴── bor-agent (root daemon) ───────────────────────────────┐
                 │  discovery: /proc/self/mountinfo + sysfs -> dm-crypt volumes            │
                 │  header inventory: cryptsetup luksDump --dump-json-metadata            │
                 │  enforcement: systemd-cryptenroll · clevis · cryptsetup                │
                 │  tamper protection: dracut drop-in, /etc/crypttab (manage mode)        │
                 └───────┬──────────────────────┬─────────────────────────────────────────┘
                         │ at boot              │ at boot (initramfs, without the agent)
                    TPM 2.0 chip          Tang server(s)  ◄── plain HTTP, blinded exchange
```

Three properties define the design:

1. **The Bor server is never in the boot path.** Boot-time unlocking is
   performed entirely by the initramfs: `systemd-cryptsetup` unseals the
   TPM enrollment, Clevis contacts Tang, or the user types the recovery
   key. A Bor server outage never prevents a machine from booting, and a
   compromise of the server never yields keys "on every boot" - only the
   escrowed recovery keys, which are separately protected (below).

2. **Bor orchestrates; the standard tools do the cryptography.** The agent
   drives `cryptsetup`, `systemd-cryptenroll` and `clevis` with fixed,
   validated arguments. Secrets pass to these tools exclusively through
   stdin and an inherited pipe - never through command lines, files or the
   environment. The only secret Bor ever generates is the recovery key
   (kernel CSPRNG, identical format to `systemd-cryptenroll
   --recovery-key`, so boot prompts and help-desk procedures are unchanged).

3. **Escrow-first ordering.** A recovery key is stored on the server
   *before* its keyslot is created on disk, and an old keyslot is wiped
   only *after* the server has confirmed the new one. At no point does a
   recovery slot exist whose secret the server does not hold.

### Where secrets live

| Secret | Location | Protection |
|---|---|---|
| Volume key | Only inside LUKS keyslots on the disk itself | Never leaves the node; Bor never reads it |
| User passphrase | Keyslot on disk | Never known to Bor |
| TPM enrollment | Sealed in the TPM, bound to PCRs | Never leaves the chip |
| Tang exchange | Nothing stored client-side; the server's key never sees client data | Blinded McCallum-Relyea exchange |
| **Recovery key** | **Bor server database, envelope-encrypted** | Per-record AES-256-GCM DEK; DEK wrapped by a KEK read from `BOR_ESCROW_KEK_FILE`, which lives **outside the database** |

The envelope encryption means a stolen database dump is useless without the
KEK file and vice versa - back them up **separately**. Each record's
authenticated data binds the ciphertext to its volume and escrow ID, so
records cannot be swapped. Deleting a key is crypto-shredding: the
ciphertext and wrapped DEK are erased. Without a configured KEK, escrow
refuses to operate rather than degrade.

A recovery key leaves the server on exactly two paths:

- **A human reveal** - dedicated permission, step-up re-authentication,
  mandatory reason, high-severity audit event, `Cache-Control: no-store`,
  and (by default) automatic rotation afterwards.
- **Server-assisted rotation** - released only to the node that owns the
  volume, only while a rotation task exists for it, at most once per
  24 hours, audited, and retired in the same run. It exists so a machine
  with no other usable credential can still rotate; it can be disabled per
  policy.

### Escrow-first rotation (two-phase commit)

Every escrow - the initial one and every rotation - follows the same
sequence, with progress (never keys) persisted so a crash resumes cleanly:

```
bor-agent                                   bor-server
   │  K ← new 256-bit recovery key (memory only)
   │── EscrowRecoveryKey(uuid, escrow_id, K) ──►  stored PENDING (envelope-encrypted)
   │◄───────────────── accepted ──────────────│
   │  cryptsetup luksAddKey  (existing credential on stdin, K on a pipe) -> slot N
   │  import systemd-recovery token · verify slot N opens with K
   │── ConfirmRecoveryKey(escrow_id, N, fingerprint) ──►  PENDING -> ACTIVE,
   │                                                      previous ACTIVE -> SUPERSEDED
   │  wipe the old Bor recovery slot(s), unlocking with K
   │── next inventory report ──►  superseded key retired once its slot is gone
   ▼  K erased from memory
```

A pending escrow that never gains a slot (agent crashed before enrolling)
expires server-side after 24 hours; a slot that never got confirmed is
detected on restart and either confirmed late or wiped as an orphan - but
only when the volume keeps another confirmed protector.

### Drift and clone detection

Every keyslot has a **fingerprint** - a hash of the volume UUID, slot index
and the slot's random KDF salt. Re-keying or replacing a slot changes it.
The server stores the fingerprint of each ACTIVE key and compares it against
every inventory report: if the fingerprint disappears, the escrowed key no
longer opens that disk (someone re-keyed it, or the header was restored from
a backup). That raises a `luks.drift` audit event and schedules a rotation -
all without the server ever touching key material.

The same reports reveal **cloned golden images**: two nodes presenting the
same LUKS UUID share one volume key. Bor raises `luks.clone_suspected` and
flags it in the UI; the only real fix is re-encrypting one of the machines.

## Server setup

1. **Create the KEK** and point the server at it:

   ```bash
   head -c 32 /dev/urandom > /etc/bor/escrow.kek
   chmod 0600 /etc/bor/escrow.kek
   # BOR_ESCROW_KEK_FILE=/etc/bor/escrow.kek
   ```

   The server logs `Recovery-key escrow enabled (KEK "file-1" …)` at
   startup. The file must hold exactly 32 bytes (raw or base64) and must
   not be group- or world-readable. See
   [KEK rotation](#configuration-reference) for replacing it later.

2. **Register Tang servers** (only if you use the Tang protector) under
   **Settings -> Tang servers** - see
   [Tang server operations](#tang-server-operations).

3. **Review who may reveal keys.** Defaults after the migration:

   | Permission | Granted to |
   |---|---|
   | `disk_encryption:view` - fleet page, volume and key *metadata* | every role that has `node:view` |
   | `disk_encryption:reveal` - reveal a recovery key | **Super Admin only** |
   | `disk_encryption:rotate` - request a rotation | **Super Admin only** |
   | `tang_server:view/create/edit/delete` | roles with `settings:manage` |

   Grant `reveal` to a help-desk role deliberately, and keep
   `BOR_ESCROW_REQUIRE_MFA=true` (the default) so revealing always requires
   a second factor.

## Creating a policy

**Policies -> Create a policy -> Disk encryption (LUKS)**. The editor is
organised as *Requirements*, three *Protector* cards, and *Advanced*.

### Requirements

| Setting | Meaning | Default |
|---|---|---|
| Require encryption | Every in-scope mount not backed by LUKS is non-compliant | on |
| Volume scope | `System volumes` (/, /usr, /var, /home, active swap) · `Specific mountpoints` · `All fixed disks` | System volumes |
| Require TPM 2.0 / Require Secure Boot | Platform requirements, reported per node | off |
| Minimum volume key size / allowed ciphers | Compliance floor; defaults are 512-bit keys (AES-256-XTS) and `aes-xts-plain64` | defaults |

Requiring encryption **never converts a disk**: an unencrypted volume is
reported (compliance item, node-drawer warning, fleet summary card), and
the remedy is reinstalling with encryption - see
[provisioning](#adoption-and-provisioning). Swap on plain dm-crypt with a
random key counts as encrypted; LUKS1 volumes are non-compliant until
converted offline (`cryptsetup convert --type luks2`).

### Protectors

**TPM 2.0** - enrolled with an explicit PCR profile:

| Profile | PCRs | Behaviour |
|---|---|---|
| Secure Boot *(default)* | 7 | Unseals while the Secure Boot configuration is unchanged; survives ordinary OS and kernel updates |
| Secure Boot + shim | 7 + 14 | Additionally bound to the shim/MOK certificates |
| Custom | your list | PCRs 0 and 2 change on firmware updates and require an explicit opt-in |

With **auto-reseal** (default on) a firmware or Secure Boot change is a
non-event: the next boot falls back to Tang or the recovery key, and once
the system is up the agent re-enrolls the TPM (audited as
`luks.tpm_reseal`, at most once per boot). TPM enrollments owned by another
FDE stack (Ubuntu's snapd TPM-FDE, openSUSE `sdbootutil`, pcrlock or
signed-PCR setups) are detected and reported *inapplicable* - Bor never
competes with them.

**Tang** - servers are picked from the registry; their confirmed signing
thumbprints are **copied into the policy**, so the policy is self-contained
and exportable, and agents refuse keys an admin never confirmed. With
several servers a threshold selects how many must be reachable (Shamir
secret sharing). The editor states the trade-off plainly: a stolen device
still unlocks while it can reach Tang.

**Recovery key** - escrow on/off, rotation interval (default 180 days,
30-730 or 0 = never), *replace after every reveal* (default on), and
*server-assisted rotation* (default on, explained above).

### Advanced

- **Initramfs handling** - `Verify only` (default): check and report.
  `Manage` (dracut systems): write the Bor drop-in, add
  `tpm2-device=auto` to the managed crypttab entries and rebuild the
  initramfs. Manage mode rebuilds the initramfs on every node the policy
  reaches - pilot it first.
- **Adopt existing enrollments** (default on) - TPM2/Tang keyslots that
  already match the policy count as managed; non-matching ones are replaced
  only after the new slot verifies. Unknown keyslot types are never touched.

### Merge semantics

When several Disk encryption policies bind to one node: `require_*` and
`recovery.escrow` are OR-ed; the rotation interval takes the smallest
non-zero value; every other setting comes from the highest-priority policy
that sets it. **Tang server lists are not merged** - the highest-priority
list wins entirely, because a union would silently widen who can unlock the
disk.

## How enforcement works on the node

Each sync runs in two phases so the UI shows fresh inventory within
seconds even when enforcement takes longer:

1. **Inventory (read-only).** Discover dm-crypt volumes by walking
   `/proc/self/mountinfo` and sysfs (through LVM and MD layers), parse each
   LUKS2 header (`cryptsetup luksDump --dump-json-metadata`), classify
   every keyslot, collect platform facts (TPM presence, Secure Boot state
   from efivars, initramfs generator, tool versions) and report to the
   server. The response carries any pending tasks (e.g. a rotation).
2. **Enforcement.** Per in-scope volume: resolve an unlock credential,
   escrow/rotate the recovery key (two-phase, above), enroll or re-seal
   TPM2, reconcile Tang bindings (bind new -> verify end-to-end -> remove
   stale), retire a consumed bootstrap slot, then handle the initramfs and
   re-report the final state and compliance.

Additional behaviour worth knowing:

- **Inventory without a policy.** Agents report their LUKS inventory on
  every connect even before any Disk encryption policy exists (server
  setting, on by default) - the fleet page answers "how many machines are
  unencrypted?" from day one.
- **Periodic re-check.** A 15-minute ticker re-reads the headers (cheap)
  so server-side drift detection stays current; a full pass including the
  TPM health check runs every 6 hours. Rotation requests from the UI reach
  connected agents immediately over the policy stream.
- **Tamper protection.** In manage mode the dracut drop-in and
  `/etc/crypttab` are watched; external edits are restored and reported
  like every other Bor-managed file (rebuilds stay rate-limited, so a
  tamper loop cannot become a rebuild storm). LUKS headers are not files -
  header changes are caught by the fingerprint comparison instead.
- **Unbinding the policy removes no protection.** Enrollments, keyslots
  and escrowed keys all stay; only Bor's own dracut drop-in is withdrawn.
- **CLI.** `bor-agent luks status` prints the local inventory;
  `bor-agent luks adopt` performs interactive adoption (below).

### Node requirements

| Component | Needed for | Notes |
|---|---|---|
| `cryptsetup` ≥ 2.4 | everything | packaged everywhere; the agent package recommends it |
| `systemd-cryptenroll` (systemd ≥ 252) | TPM2 protector | dracut-based systems (Fedora, RHEL 9/10, Ubuntu ≥ 25.10) |
| `clevis-luks` + `clevis-dracut` | Tang protector | missing tooling under a Tang policy is **non-compliant**, not inapplicable - a required control is absent |
| dracut initramfs | TPM2 at boot, manage mode | initramfs-tools systems (Debian, Ubuntu Server/≤ 24.04) get recovery-key escrow today; their TPM2/Tang boot path is Phase 2 |

## Adoption and provisioning

Adding any keyslot requires an existing unlock credential. The agent
resolves one per volume in this order, preferring local sources so a key
leaves the server only when nothing else works:

1. an existing **TPM2** enrollment that unseals in the current PCR state;
2. an existing **Clevis/Tang** binding (existing NBDE fleets adopt with no
   interaction at all);
3. a **bootstrap key file** `/etc/bor/luks-bootstrap/<luks-uuid>.key`
   placed by provisioning - used once, then its keyslot is wiped and the
   file deleted;
4. **server-assisted rotation** (only when a key was escrowed before);
5. a human running `sudo bor-agent luks adopt` and typing the current
   passphrase once (the passphrase slot stays).

Until one succeeds the volume reports `luks:adoption` non-compliant with a
pointer to this section.

**Provisioning new installs** (the preferred path): have the installer
encrypt with a random per-host bootstrap passphrase and drop it into the
installed system. Kickstart example:

```
%pre
PASS=$(head -c 18 /dev/urandom | base64)
echo "part / --fstype=xfs --encrypted --luksversion=luks2 --passphrase=${PASS}" > /tmp/part-include
echo "${PASS}" > /tmp/bootstrap.key
%end

%include /tmp/part-include

%post --nochroot
UUID=$(blkid -s UUID -o value /dev/sda3)   # the LUKS container
install -D -m 0600 /tmp/bootstrap.key "/mnt/sysimage/etc/bor/luks-bootstrap/${UUID}.key"
%end
```

(Ubuntu autoinstall: set the `storage` layout password and copy the file in
`late-commands`.) On its first sync the agent escrows a recovery key,
enrolls the configured protectors, wipes the bootstrap slot and deletes the
file - the bootstrap secret's exposure window is the provisioning run only.

## Recovering a machine (help desk)

1. The user reads the volume identifier off the boot prompt (on
   Fedora/RHEL the mapping name is `luks-<UUID>`).
2. Open **Fleet -> Disk Encryption** and search - hostname, LUKS UUID or
   key-ID prefix all work, with or without dashes.
3. **Show recovery key…** Enter a reason or ticket number (stored in the
   audit event), then re-authenticate: your password, plus your TOTP code
   when your account has one enrolled. This *step-up* produces a
   single-use, five-minute token; possession of a logged-in browser session
   alone is not enough to reveal a key.
4. Read the key to the user (eight groups of eight characters, typeable on
   any keyboard layout). It is hidden again after two minutes.
5. Once the machine reconnects, the key is **rotated automatically**
   (default policy setting) - a key that was ever spoken aloud does not
   stay valid.

Every reveal is a `recoverykey.reveal` audit event (severity: high) with
actor, volume, escrow ID and reason; failed attempts are
`recoverykey.reveal_denied`. The node drawer on the Nodes page offers the
same actions for a single machine.

## Recovery-key lifecycle

```
pending ──confirm──► active ──rotation──► superseded ──slot gone──► retired ──retention──► destroyed
   └─ no slot within 24 h ─► expired (shredded immediately)
```

Rotations are triggered by: the policy interval (default 180 days), a
reveal (default on), the admin **Rotate now** action, drift detection, or a
server-assisted release. The hourly server janitor expires stale pending
keys, alerts on unconfirmed releases, schedules due rotations, and
crypto-shreds keys past retention.

Retention is deliberate rather than immediate:

- **Retired keys** stay revealable for `BOR_ESCROW_RETIRED_RETENTION_DAYS`
  (default 30) - a disk restored from an older LUKS header backup needs its
  older key.
- **Keys outlive node deletion.** Decommissioning a node orphans its
  volumes instead of deleting their keys (a drawer may still hold the
  disk); orphaned keys are shredded after
  `BOR_ESCROW_ORPHAN_RETENTION_DAYS` (default 90). This differs from
  Active Directory, where deleting the computer object silently deletes its
  BitLocker keys.

## Tang server operations

[Tang](https://github.com/latchset/tang) is a small stateless service you
run yourself (typically two instances for redundancy); clients unlock via a
blinded exchange, so Tang never sees key material or client identity, and
deliberately has no client authentication - **network reachability is the
credential**. Keep Tang servers reachable only from networks where
unattended unlocking should work.

- **Registering** (Settings -> Tang servers -> Add): Bor fetches the
  advertisement and shows the signing-key thumbprints; compare them with
  `tang-show-keys` on the Tang host before confirming. This makes
  trust-on-first-use explicit and human-verified - agents only ever bind to
  keys an admin confirmed, and never pass Clevis's `-y` (which would skip
  thumbprint verification entirely).
- **Key rotation**: rotate on the Tang host (`tangd-rotate-keys`, keeping
  the old keys as hidden files). Bor's periodic check flags the server as
  *New key advertised*; open it and confirm the new thumbprint. The new key
  becomes preferred while old ones stay accepted; agents re-bind each
  volume (bind to the new key -> verify -> remove the stale binding - never
  `clevis luks regen`, which trusts blindly). The registry shows **bound
  volumes per signing key** from the inventory reports: when the old key's
  count reaches zero, its hidden files can be deleted on the Tang host.
  This fleet view is exactly what stock NBDE lacks.

## Compliance reference

Each bound policy reports the merged result; per-item detail appears on the
Compliance page.

| Item | Key | Non-compliant when | Inapplicable when |
|---|---|---|---|
| `luks:encryption` | mountpoint | not encrypted, or LUKS1 | encryption not required |
| `luks:cipher` | volume | cipher not allowed, or key below the minimum | - |
| `luks:recovery` | volume | no confirmed key, drift, or overdue | escrow off; externally managed |
| `luks:tpm2` | volume | missing/wrong PCRs, or stale and reseal failed | no TPM (unless required); externally managed; non-dracut system |
| `luks:tang` | volume | binding missing or stale, or clevis not installed | Tang off |
| `luks:initramfs` | volume | boot-time unlock support missing (verify mode) | no automatic protector |
| `luks:bootstrap` | volume | the provisioning slot still exists | none used |
| `luks:adoption` | volume | no unlock credential available | - |
| `platform:tpm2` / `platform:secureboot` | node | requirement not met | not required |

`ERROR` states indicate the check or operation itself failed (unreadable
header, enrollment failure, escrow not configured on the server) and carry
the underlying message.

## Security model and limitations

What the design defends against - and, deliberately documented, what it
does not:

- **Server compromise ≠ mass unlock at boot.** The server is not in the
  boot path; compromising it yields at most the escrowed recovery keys,
  and only together with the KEK file. This is the same trust class as
  BitLocker keys in AD. If that residual risk is unacceptable, the roadmap
  has a sealed-escrow mode (agents encrypt to a public key; reveals need an
  offline ceremony).
- **Rotating a keyslot is not revocation.** Anyone who copied the LUKS
  header *and* knew an old key - or who extracted the volume key from a
  running system - retains access regardless of rotation. True revocation
  requires re-encrypting the volume key (a Phase 3 research item).
- **Tang trusts the network.** A stolen device unlocks while it can reach
  the Tang server. Mitigations: strict network placement, combining Tang
  with TPM2 (Phase 2 threshold binding), and the planned Bor Tang responder
  with per-node keys and instant "mark as lost" revocation.
- **Cloned images share a volume key.** Detected and flagged, not fixable
  without re-encryption.
- **Forward the audit stream.** The database audit log has no hash chain;
  tamper-evidence for `recoverykey.*` events relies on off-box syslog
  forwarding ([`audit_logs.md`](audit_logs.md)).

Cryptography: recovery keys come from the kernel CSPRNG and use
PBKDF2-HMAC-SHA512 keyslots (FIPS-approved; the key has 256 bits of entropy,
so KDF stretching adds nothing); escrow is AES-256-GCM envelope encryption;
volume encryption is whatever LUKS is configured with - the compliance
default demands `aes-xts-plain64` with 512-bit keys (AES-256-XTS).

## Troubleshooting

| Symptom | Likely cause / fix |
|---|---|
| Editor shows "escrow is not configured", `luks:recovery` is ERROR | `BOR_ESCROW_KEK_FILE` unset, unreadable, wrong size or too-open permissions - check the server startup log |
| `luks:adoption` non-compliant | No usable credential; run `sudo bor-agent luks adopt` once, or provision a bootstrap key |
| `luks:tpm2` inapplicable: "managed by …" | Another FDE stack owns the TPM (snapd, sdbootutil, pcrlock); this is by design |
| `luks:tpm2` non-compliant after a firmware update, auto-reseal off | Expected: the PCRs changed. Enable auto-reseal or rotate manually |
| `luks:tang` non-compliant: "clevis is not installed" | Install `clevis-luks` and `clevis-dracut` on the node |
| `luks:initramfs` non-compliant in verify mode | The message names the missing piece (`tpm2-tss` dracut module, Clevis module, crypttab option, `rd.neednet=1`); fix manually or switch the policy to manage mode |
| Reveal returns 403 | Missing `disk_encryption:reveal`, failed step-up, or MFA required but not enrolled (`BOR_ESCROW_REQUIRE_MFA`) |
| Rotation pending for a long time | The node is offline or stuck at a boot prompt; the rotation runs on its next connect. `bor_luks_recovery_keys_overdue_total` alerts on this |
| Tang server shows "New key advertised" | Someone rotated the Tang keys; confirm the new thumbprint against `tang-show-keys` |

## Configuration reference

### Server (`.env` / `server.yaml` -> `disk_encryption:`)

| Variable | Default | Purpose |
|---|---|---|
| `BOR_ESCROW_KEK_FILE` | - (escrow disabled) | 32-byte KEK file, mode 0600, outside the DB |
| `BOR_ESCROW_KEK_ID` | `file-1` | Label stored on records wrapped with the current KEK |
| `BOR_ESCROW_KEK_PREVIOUS_FILES` | - | Comma-separated `id=path` old KEKs, readable during rotation; a background job rewraps every record to the current KEK |
| `BOR_ESCROW_REQUIRE_MFA` | `true` | Require a second factor during the reveal step-up |
| `BOR_ESCROW_RETIRED_RETENTION_DAYS` | `30` | How long rotated-away keys stay revealable |
| `BOR_ESCROW_ORPHAN_RETENTION_DAYS` | `90` | How long a deleted node's keys are kept |

To rotate the KEK: create a new file, set it as `BOR_ESCROW_KEK_FILE` with
a new `BOR_ESCROW_KEK_ID`, list the old one in
`BOR_ESCROW_KEK_PREVIOUS_FILES`, restart; remove the old entry once the
janitor has rewrapped all records (only 32-byte DEKs are ever rewrapped,
never recovery keys).
